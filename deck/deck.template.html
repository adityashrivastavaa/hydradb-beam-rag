Storing and retrieving memory

Three ways to give an agent memory

01

A memory file

Append facts to MEMORY.md, load the whole file into every prompt.

Best for a handful of preferences

Breaks when the file outgrows the context window

02

Vector store + chunks

Chunk everything, embed it, fetch the chunks closest to the question.

Best for pinpoint factual lookups

Breaks on time, contradictions and big-picture questions

03

A graph

Extract entities and relations, connect them over time, traverse to answer.

Best for evolving, connected memory

Holds accuracy as memory grows

03
01 · The memory file

MEMORY.md works, until it doesn’t

Good: zero infrastructure, perfectly transparent, great for a handful of preferences.

Breaks at scale: every turn pays for every memory; the context bloats, then the window overflows.

04
02 · Vector store + chunking

Chunk it, embed it, hope it comes back

Great at

Pinpoint questions whose answer sits verbatim in one chunk: “Which port is the memory store on?”

Struggles with

Anything that needs time, consistency or the big picture (next two slides).

02 · Why vectors get noisy at scale

More memories, less separation

A few hundred chunks

clear winner

Hundreds of thousands

photo finish

Real embeddings are anisotropic: they bunch into a narrow cone. As the store grows, the top-k neighbours of a query end up a hair apart in cosine, so a slightly different phrasing returns a different set. (Illustrative 2-D projection; scores are the true cosines of the plotted points.)

06
02 · Where vector memory breaks

Similarity measures relevance,
not answerability

Time

“Deadline is June 25” and “deadline moved to July 2” look equally relevant. Nothing says which is current.

What a graph adds

Edges carry timestamps, so the newest fact can win.

Staleness

Old facts are never retired, so they keep winning retrieval long after they stopped being true.

What a graph adds

A superseded relation is marked as such, not just outranked.

Contradictions

“I’ve shipped it” vs “I’ve never built it”: both come back, with no notion that they conflict.

What a graph adds

Both claims attach to the same entity, so they surface side by side.

Big-picture questions

“Summarise how my project evolved” needs hundreds of chunks, not the top 10. A deep-research agent can do it, at a steep cost per question.

What a graph adds

Walk one neighbourhood instead of reading every chunk.

07
03 · Graph memory

Store chunks vs. connect context

  • Every chunk still lands, and entities and relations are extracted from it.
  • Facts link across sources and sessions: who did what, when, and what it blocked.
  • Retrieval walks the neighbourhood of what the question mentions, instead of ranking isolated chunks.

Try it yourself

Graph memory on your laptop, in five steps

Clone the repo

git clone https://github.com/adityashrivastavaa/hydradb-beam-rag cd hydradb-beam-rag

Build HydraDB (pinned, open source)

brew install cmake pkg-config llvm suite-sparse \ cleishm/neo4j/libcypher-parser HYDRADB_DIR=~/src/hydradb scripts/install_hydradb.sh

Start it (own terminal)

HYDRADB_DIR=~/src/hydradb scripts/start_hydradb.sh

Python env + load the graph

scripts/setup_python.sh && source .venv/bin/activate python -m app.loader # ~2 min, 9,227 relations

Serve the app

uvicorn app.server:app --port 8000 # open http://localhost:8000

Optional: answers from Claude

export ANTHROPIC_API_KEY=… # then “Answer with Claude”
macOS (Apple Silicon) · verified from a fresh clone
